# تيوزدية — منصة الورش والحجوزات والحضور | Tuesday Platform

> **إصدار 1.0.4 — تحديث الربط:** أصبحت المتغيرات الإلزامية ثلاثة فقط: `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` و`TICKET_SIGNING_SECRET`. يجب إتاحة متغيرات `VITE_` ضمن نطاق **Builds وFunctions**. أسماء `SUPABASE_URL` و`SUPABASE_ANON_KEY` اختيارية وموروثة؛ إذا وُجدت يجب أن تطابق القيم العامة. السر الأخير يُولد ويُحفظ في Netlify ولا يوضع في GitHub. راجع [الدليل الرئيسي](../README.md) قبل النشر.

**مشروع موقع حقيقي، مبني بأساس واحد:** Vite + React + TypeScript للواجهة، Supabase PostgreSQL للمصادقة والبيانات والملفات، وNetlify Functions لحماية التذاكر وتسجيل الحضور.

> ⚠️ **توضيح حالة التسليم:** هذا *كود مصدر للتشغيل والنشر* وليس حساب Netlify أو Supabase مرتبطًا أو خدمة مدفوعات مفعلة. يجب تنفيذ الإعدادات والاختبارات أدناه قبل استقبال مستخدمين أو مدفوعات فعلية. صفحة العرض التجريبية لا تحفظ أي طلب عند عدم ضبط Supabase. لم يتم التحقق من البناء عبر `npm install` في بيئة التسليم التي لا تسمح باتصال npm؛ ينبغي تشغيل `npm install && npm run build` محليًا وعلى Netlify.

## المزايا

- واجهة **Mobile-first / RTL** وفق هوية تيوزدية الكحلية والسماوية والشعار الأصلي، وصفحات عامة للورش والمواقع والصور.
- **PWA** (تثبيت على الشاشة الرئيسية)، وملف `manifest.webmanifest` وService Worker للأصول الثابتة فقط؛ العمليات الحساسة تحتاج الاتصال.
- مصادقة OTP عبر **البريد الإلكتروني** باستخدام Supabase Auth؛ الملف الشخصي يشمل الاسم والجوال.
- طلب حجز مستقل لكل مشارك وورشة، **مراجعة إدارية إلزامية** قبل إصدار تذكرة.
- دفع خارجي عبر رابط يتم إدخاله من الإدارة؛ **مطابقة دفع يدوية** بواسطة المراجع، وليست عملية دفع آلية، مع حظر اعتماد الحجز قبل التحقق.
- حفظ الرقم المرجعي، تاريخ المراجعة، وجميع قرارات الاعتماد/الرفض في `audit_logs`.
- توقيع رمز QR بخوارزمية HMAC في Netlify Functions؛ فحص هوية الموظف في الخادم وقاعدة البيانات؛ قيد UNIQUE مع معاملة لتسجيل **حضور واحد فقط** لكل حجز.
- لوحة إدارة ورش/صور/تسجيلات/مراجعات/كاميرا QR/تقارير، وتصدير **XLSX حقيقي** للحجوزات والحضور والدفع والاستردادات والورش.
- حسابات وصلاحيات للفريق: owner, admin, reviewer, checkin.
- حالة استرداد عند رفض طلب مدفوع تم التحقق منه، وتتطلب تنفيذ رد المبلغ فعليًا في مزود الدفع قبل توثيق إتمامه.

## متطلبات أولية

1. حساب **Supabase** مع مشروع جديد (PostgreSQL + Auth + Storage).
2. حساب **Netlify** متصل بمستودع GitHub/GitLab يحتوي على ملفات المشروع.
3. Node.js **22 أو أحدث** للتطوير والبناء.
4. مزود إرسال بريد إنتاجي لإرسال رموز OTP عند التشغيل الحقيقي. في Supabase > Authentication > Email Templates > Magic Link غيّر قالب الرسالة ليعرض `{{ .Token }}` بدل الرابط وحده؛ راجع إعدادات Supabase والتوثيق.
5. رابط دفع خارجي من جهة موثوقة، وصلاحية دخول إلى لوحة المزود لإجراء مطابقة يدوية.

## نشر Netlify — الطريقة الصحيحة

> **لا ترفع ZIP الكود المصدري إلى منطقة Drag-and-Drop** وتظن أن Netlify Functions ستعمل؛ رفع مجلد `dist` فقط لا ينشر Functions. اربط مشروع Git واستخدم إعدادات البناء الآلية، أو انشر عبر Netlify CLI الداعم للـ Functions.

1. فك الملف ZIP وارفع **محتويات مجلد المشروع** إلى مستودع Git (وليس ZIP فقط).
2. في Supabase > SQL Editor نفذ الملف `supabase/migrations/001_initial.sql` **مرة واحدة** في قاعدة بيانات جديدة، ثم تحقّق من نجاح الإنشاء.
3. في Authentication > URL Configuration أدخل رابط موقع Netlify في **Site URL**، وأضفه إلى Allowed Redirect URLs. لا تُفعّل دخول OAuth أو SMS ما لم تضبطهما.
4. أنشئ حساب المالك بتسجيل الدخول إلى الموقع بعد نشر النسخة الأولى أو من بيئة التطوير المتصلة بـ Supabase.
5. امنح صلاحية المالك **مرة واحدة عبر SQL Editor** بعد وجود حسابه:

```sql
insert into public.staff_members(user_id, role)
select id, 'owner' from auth.users where email = 'you@example.com'
on conflict (user_id) do update set role='owner', active=true;
```

6. Netlify > Add new project > Import an existing project > اختر المستودع، مع إعدادات:
   - Build command: `npm run build`
   - Publish directory: `dist`
   - Base directory: جذر المشروع
   - Functions: `netlify/functions` (محدد في `netlify.toml`)
7. أضف **متغيرات البيئة عبر Netlify UI** مع تحديد بيئات Builds وFunctions حسب الحاجة:

| المتغير | المكان | محتواه |
|---|---|---|
| `VITE_SUPABASE_URL` | Build | عنوان مشروع Supabase |
| `VITE_SUPABASE_ANON_KEY` | Build | مفتاح Supabase العام (publishable/anon) |
| `SUPABASE_URL` | Functions Runtime | العنوان نفسه |
| `SUPABASE_ANON_KEY` | Functions Runtime | المفتاح العام نفسه |
| `TICKET_SIGNING_SECRET` | Functions Runtime **سري** | سلسلة عشوائية قوية لا تقل عن 32 حرفًا، يوصى 64+ |

**لا تستخدم `VITE_` مع الأسرار. لا تحتاج Service Role Key لهذا المشروع، ولا يجب وضعه في كود الواجهة.**

8. Deploy. افتح الموقع عبر HTTPS، ثم اختبر تسجيل الدخول والحجز والدفع اليدوي والموافقة وإصدار التذكرة ومسحها مرة ورفض الثانية.
9. من حساب المالك افتح `/admin` وأنشئ ورشة **مسودة** أولًا، ثم اختبر نشرها واستعراضها.
10. اضبط نطاقًا خاصًا إن أردت. بعد تثبيت الرابط النهائي حدّث Site URL في Supabase.

## تطوير محلي

```bash
npm install
cp .env.example .env
# اكتب المفاتيح الفعلية بالمتغيرات المذكورة
npm run dev           # الواجهة فقط؛ لن تعمل /api/ticket أو /api/checkin هنا
npm run check         # فحص TypeScript
npm run build         # إنشاء dist، مع الـ PWA
npm run test:static   # تدقيق ثابت للهيكل والقيود
```

لتجربة Netlify Functions محليًا استخدم `netlify dev` من Netlify CLI بعد تثبيته، بدل `npm run dev` وحده، واحرص على توفر متغيرات البيئة الخمس. لا تشارك ملف `.env`.

## ماذا يحدث في تسجيل الحضور؟

1. يعتمد المراجع طلب الحجز **بعد** التحقق من الدفع (إن كان مدفوعًا).
2. تنشئ PostgreSQL صفًا في `tickets` مربوطًا بالحجز. QR ليس مجرد رقم الحجز؛ الواجهة تستدعي Netlify Function محمية لإرجاع `TUE1.ticket_id.HMAC`.
3. ماسح موظف الاستقبال يرسل الكود إلى `POST /api/checkin` عبر HTTPS وبـ JWT صالح.
4. Function تتحقق من صحة توقيع HMAC باستخدام سر على الخادم، ومن صلاحية الموظف، ثم تستدعي RPC `check_in_ticket`.
5. RPC تقفل صف التذكرة `FOR UPDATE`، وتتحقق من اعتماد الحجز والوقت والحالة، وتضيف `checkins` بقيد UNIQUE وتغير الحالة إلى `used` **داخل معاملة واحدة**.
6. إن أعيد المسح تعيد `ALREADY_USED` ولا تضيف سجل حضور. في حالة انقطاع الاتصال لا تُعرض رسالة نجاح.

## تسلسل حالات الحجز

- مجانية: `pending_review` → موافقة → `approved` + تذكرة.
- مدفوعة: `awaiting_payment` → إبلاغ العميل بالمرجع → `pending_review` + `reported` → مراجع يتحقق من العملية في بوابة الدفع → `verified` → موافقة → `approved` + تذكرة.
- يمكن للمراجع طلب الاستكمال أو الرفض. رفض طلب مدفوع متحقق منه ينشئ حالة استرداد (`refund_cases`) تحتاج معالجة.
- **الضغط على رابط الدفع ليس دليلًا على السداد**، ولا توجد Webhooks أو استردادات آلية قبل عقد التكامل مع مزود دفع محدد.
- حجز المقاعد أثناء الدفع مؤقت 30 دقيقة، وحين تنتهي مهلة الحجز يتطلب إعادة فحص السعة قبل اعتماد بلاغ دفع متأخر. يجب أن تنشر الإدارة سياسة واضحة لمثل هذه الحالات والاسترداد.

## الإعدادات والخصوصية قبل الإطلاق

- سياسة خصوصية نهائية، مدة الاحتفاظ، حقوق المشاركين، سياسة الإلغاء والاسترداد، وسائل تواصل رسمية.
- راجع مدى توافق مكان الاستضافة/البيانات مع الأنظمة السعودية المنطبقة وخصوصًا نظام حماية البيانات الشخصية، وراجع مكان تخزين البيانات في Supabase.
- فَعِّل حماية متعددة العوامل لحسابات الإدارة حيثما تتاح، واضبط حدود رسائل OTP.
- فحص وصول الأدمن وRLS بكل دور، واختبار أجهزة حضور متزامنة، واختبار نسخ احتياطي واستعادة فعليًا.
- عدّل صورة الغلاف والعناوين والمواعيد؛ المحتوى في وضع العرض مجرد أمثلة توضيحية.
- خدمة تأكيد عبر الرسائل SMS وWebhooks الدفع والإشعارات الحية خارج نطاق النسخة التي تسلّم دون بيانات مزود الخدمة، ويمكن دمجها لاحقًا.

## مستويات الاختبار

- `npm run test:static`: يفحص توافر الملفات والمنطق الأمني الأساسي **ولا يغني عن اختبار النظام الحي**.
- `npm run check` و`npm run build`: يُشغَّلان عندما تكون التبعيات متاحة.
- قبل الإنتاج: اختبر حجزًا مدفوعًا ومجانيًا في قاعدة Supabase حقيقية، ورابط الدفع لدى مزود الخدمة، ومراجعة الطلب، وسجل التدقيق، ومسح أول وثانٍ ومن جهازين في اللحظة نفسها، وتصدير Excel وفتحه.

**ملاحظة مهمة:** دون حساباتك ومفاتيح Supabase/Netlify ومزود الدفع، لا يمكنني تفعيل قواعد البيانات الحقيقية أو اختبار عمليات مالية حقيقية. لا تصف هذا النظام بأنه بدأ بالفعل استقبال حجوزات أو أموال قبل إكمال هذه الخطوات.
